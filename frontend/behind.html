order.hpp

Defines an order: ID, side, type, price, quantity, and timestamp. Key topics: market data modeling, enum types, unique identifiers.

trade.hpp

Defines executed trades with buyer, seller, price, quantity, and timestamp. Key topics: execution records and trade tape output.

order_book.hpp / order_book.cpp

Maintains bid and ask price levels using ordered maps and FIFO deques. Key topics: price-time priority, cancellation, modification, active-order lookup, matching loops.

matching_engine.hpp / matching_engine.cpp

Wraps the order book and records metrics whenever orders, trades, cancels, and modifies occur. Key topics: engine boundary, aggregation, matching orchestration.

metrics.hpp / metrics.cpp

Tracks orders, trades, volume, latency, fill delay, cancels, modifies, missed opportunities, and slippage. Key topics: counters, averages, performance telemetry.

csv_replay.hpp / csv_replay.cpp

Parses timestamped CSV rows into replay events and sorts them by time. Key topics: schema detection, CSV parsing, replay sequencing, validation errors.

csv_files.hpp / csv_files.cpp

Discovers replay CSVs, validates uploads, stores uploaded files, and returns metadata. Key topics: filesystem traversal, safe paths, upload validation.

event_queue.hpp / event_queue.cpp

Stores delayed strategy actions by timestamp and caps queue growth. Key topics: priority queues, deterministic event ordering, latency simulation, backpressure.

object_pool.hpp

Provides RAII handles for reusable preallocated objects. Key topics: heap ownership, object reuse, allocation efficiency, cleanup.

os_concepts.hpp

Centralizes lifecycle, thread, and memory diagnostics. Key topics: process phases, named threads, stack versus heap visibility, synchronized logging.

strategy.hpp / strategy.cpp

Defines the strategy interface and implements market making, momentum, mean reversion, and imbalance models. Key topics: polymorphism, order generation, active order management, P&L attribution.

optimizer.hpp / optimizer.cpp

Builds parameter grids, splits walk-forward windows, evaluates strategies, ranks configurations, and produces curves. Key topics: grid search, walk-forward testing, return/risk metrics.

live_server.cpp

Serves the frontend, streams state through Server-Sent Events, receives commands, handles uploads, runs replay, and triggers optimization. Key topics: process lifecycle, lightweight HTTP, SSE, JSON assembly, threads, synchronization.

app.html / app.js / styles.css

Builds the trading and systems interface, charts, controls, upload flow, optimization dashboard, and docs pages. Key topics: responsive UI, canvas charts, live rendering, queue and thread observability.

tests/

Assert-based C++ tests verify matching, lifecycle behavior, latency, replay parsing, CSV discovery, strategy behavior, optimizer correctness, queues, pools, and race-prevention scenarios. Key topics: scenario testing, stress testing, regression safety.

Challenges I Encountered And Overcame

I had to make cancellation and modification safe without breaking price-time priority. I solved that by tracking active order IDs, removing empty price levels, and treating price changes as a reinsertion while same-price quantity edits keep priority.

I also had to prevent latency from feeling cosmetic. I overcame that by routing strategy submissions, cancels, and modifies through a timestamped event queue, so delayed orders can actually miss fills or receive worse prices.

CSV handling became tricky because market data files are not always identical. I handled that by adding schema detection, upload validation, helpful parse errors, and a metadata-driven dropdown instead of requiring manually typed paths.

The optimizer needed to compare strategies fairly. I solved that by replaying the same event data across every parameter configuration and separating in-sample training windows from later out-of-sample test windows to avoid lookahead bias.

The systems layer needed to be visible without distracting from the simulator. I added bounded queues, named thread roles, lifecycle logs, synchronization notes, and a dashboard panel that surfaces those concepts in live state.

Finally, the frontend could have become overwhelming. I kept it usable by separating live trading, replay controls, order lifecycle state, systems runtime, strategy comparison, optimization results, and documentation into distinct pages and panels.
